# Load tests (k6) — proper-scale

This harness measures the proper-scale stack through nginx: three WebSocket message services, a presence service, a PostgreSQL outbox relay, Kafka, and Redis delivery. It uses the same k6 WebSocket model and summary columns as the single-instance and naive-scale experiments.

Each VU opens one long-lived WebSocket, joins one room, and sends one message every `SEND_INTERVAL` seconds in throughput mode. Connections ramp over `RAMP` seconds. Message sends begin after the connection ramp, with up to one second of jitter, so room members are present before the measured delivery window without synchronizing every sender.

Room and client IDs are generated by k6 and passed in the WebSocket handshake. Proper-scale has no REST room or user setup endpoint. Rooms use the nginx consistent hash on `room_ids`, so all clients in one room land on the same message-service instance. Message events still pass through PostgreSQL, the outbox relay, Kafka, the delivery service, Redis, and the room's instance.

## Run

Start the stack from this directory:

```powershell
docker compose up -d --build
```

Run one scenario with host k6:

```powershell
k6 run -e ROOMS=10 -e USERS=5 -e RAMP=150 -e DURATION=30 -e SEND_INTERVAL=10 loadtest/chat_load.js
```

Run the full 4×3 matrix (12 cells, up to 10,000 concurrent sockets):

```powershell
./loadtest/run-matrix.ps1
./loadtest/run-matrix.ps1 -Rooms 1,10 -Users 2,5 -Ramp 60 -Duration 60
```

The matrix runner uses native k6 from `PATH` and writes JSON summaries under `loadtest/results/matrix/`.

## Find connection and throughput limits

The limit runner rebuilds the stack, waits for the message services' database readiness through nginx, restarts all three message services between steps, and runs containerized k6 on the Compose network by default. It leaves Kafka's named data volume in place and uses unique room IDs for each k6 run.

Connection ceiling:

```powershell
./loadtest/run-limits.ps1 -Scenario conn -Steps 5000,10000,20000,40000,60000
./loadtest/summarize.ps1 -Dir loadtest/results/3x165m-proper/conn
```

Throughput at a fixed 10,000 sockets, with 1,000 rooms of 10 users:

```powershell
./loadtest/run-limits.ps1 -Scenario tput -Rooms 1000 -Users 10 -Steps 20,15,10,9,8,7,6,5,4
./loadtest/summarize.ps1 -Dir loadtest/results/3x165m-proper/tput
```

The highest delivered rate with at least 98% completeness and WebSocket errors within the teardown budget is the throughput ceiling. Completeness is `received events / (sent messages × users per room)`. A result above 100% can indicate duplicate delivery. The latency threshold is looser than the other variants because proper-scale adds Kafka and a separate delivery service after the outbox.

`-NativeK6` uses host k6 instead of a container. `-KeepUp` leaves the Compose stack running when the sweep finishes. `-NoRestart` keeps the message-service processes between sweep steps.

## Compare

The summarizer writes `summary.md` and `summary.csv` beside the JSON files and supports the same `-Compare` option:

```powershell
./loadtest/summarize.ps1 -Dir loadtest/results/3x165m-proper/tput -Compare ../naive-scale/loadtest/results/3x200m/tput
```

The three message-service containers each have a 165 MB limit, for a 495 MB aggregate. Proper-scale also uses separate presence, delivery, and outbox-relay processes; their combined 260 MB limits are additional. Kafka has no container memory limit in the current Compose file. Record those differences when comparing results.

## Metrics

| Metric | Meaning |
| --- | --- |
| `ws_connecting` | Total duration of the WebSocket connection request; summaries show p90/p95 in milliseconds. Connection-only summaries omit message latency columns. |
| `msg_e2e_latency` | Message send to room-event receive, including database, relay, Kafka, delivery, and Redis; shown in throughput summaries |
| `msgs_sent` / `sent_count` | Send requests issued by k6; throughput summaries include the total count |
| `msgs_accepted` / `accepted_count` | Messages acknowledged as accepted by the service; this is the successful-send count in throughput summaries |
| `msgs_received` | Room events received by k6 clients, including sender echoes |
| `msgs_rejected` | Rejected acknowledgements |
| `ws_errors` | WebSocket errors and failed handshakes |

The outbox relay polls every one second by default. A load result is not recorded in the baseline until the corresponding sweep has been run on the target machine.
